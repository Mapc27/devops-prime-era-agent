# 05. Память агента

## 1. Что агенту нужно помнить

| Что | Пример | Время жизни | Как меняется |
|---|---|---|---|
| Ход текущего расследования | гипотезы, доказательства E1..En, вердикты | минуты | растёт по ходу графа |
| Прошлые инциденты | «redis упал → рестарт помог» | месяцы, ценность падает | добавляется после каждого инцидента |
| Факты об инфраструктуре и людях | «БД — PostgreSQL 17», «дежурит Alex» | до изменения | **устаревают**: новое утверждение отменяет старое |
| Процедуры | runbooks, skills | версии в git | правятся людьми |

## 2. Почему «голый» RAG не подходит

1. **Нет времени.** Векторный индекс вернёт и «PostgreSQL 15», и «мы мигрировали на 17» — оба семантически близки к вопросу. Модель выберет произвольный. Нужна **валидность во времени** и механизм инвалидации.
2. **Нет структуры и связей.** «api зависит от redis» + «redis упал» → вывод требует связи сущностей (граф), а не top-k похожих чанков.
3. **Эмбеддинги не различают детали.** В нашем тесте косинус между «runs PostgreSQL 15» и «runs PostgreSQL 17 (migrated from 15)» ≥ 0.95 — классический RAG/дедуп посчитал бы их дубликатом (мы поймали этот баг в evals и добавили проверку чисел и токенов).
4. **Нет записи.** RAG — read-only поверх корпуса; агенту нужно *учиться*: писать эпизоды и факты, обновлять, забывать.
5. **Нет приоритизации по полезности и свежести.** Старый неудачный эпизод ранжируется так же, как вчерашний успешный.
6. **Контекст-бюджет.** Top-k чанков «на всякий случай» раздувают контекст слабой локальной модели (у Jev-like моделей рабочий контекст ~2–8k токенов).

## 4. Выбранная архитектура памяти (3 слоя + procedural)

| Слой | Хранилище | Запись | Чтение | Актуальность |
|---|---|---|---|---|
| **L1 Working** (short-term) | LangGraph state + `AsyncSqliteSaver` | каждый узел графа | весь state текущего run'а | живёт один run; переживает interrupt/рестарт процесса |
| **L2 Episodic** | SQLite: эпизоды + эмбеддинги (`embeddinggemma-2`) | Scribe после инцидента: симптомы, причина, фикс, исход, skill, шаги | гибрид: `0.55·cos + 0.30·BM25 + 0.15·recency` × вес исхода | recency с полураспадом 30 дней, вес `resolved=1.0 / иначе 0.7`, счётчик использования, TTL-очистка неиспользуемых старше 180 дней |
| **L3 Semantic** (long-term) | SQLite: факты с `valid_from / valid_to / recorded_at / superseded_by` | `learn` (из сообщений), Scribe | только активные **на момент `as_of`** | **bi-temporal инвалидация** (идея Graphiti): кандидаты по косинусу/subject → Jev-like `noul` «новый факт отменяет старый?» → старый закрывается, история сохраняется; дедуп = косинус ≥ 0.95 **и** одинаковые числа/токены |
| L0 Procedural | `skills/*/SKILL.md`, `persona/*.md` в git | человек (PR) | progressive disclosure: роутер видит описания, агент — тело выбранного skill | версионирование git |

**Почему так, а не Graphiti/Mem0 целиком:**
- Мы взяли **идею** Graphiti (bi-temporal факты, инвалидация вместо перезаписи, гибридный поиск), но заменили дорогие шаги:
  - извлечение сущностей/рёбер несколькими LLM-вызовами → один structured-вызов light-модели (`Facts` JSON schema);
  - решение «противоречит ли» большой LLM → **Jev-like decision model** (`noul`, ~0.3 с, вероятность + порог), это ровно её профиль;
  - Neo4j → SQLite (одна зависимость, файл в volume агента).
- Mem0 перезаписывает факты (UPDATE/DELETE) — теряется история «что мы знали в момент инцидента», важная для постмортемов.

## 5. Недостатки выбранного решения

- Нет настоящего графа сущностей: связи «api → redis» не выводятся транзитивно (сейчас они в `INFRA.md` как статический контекст).
- Линейный перебор эмбеддингов в Python — нормально до ~10⁴ записей; дальше нужен ANN-индекс (sqlite-vec / pgvector / Qdrant).
- Инвалидация зависит от качества Jev-like модели (контекст ~2k токенов, калибровка не гарантирована); ошибочно закрытый факт исчезнет из выдачи (но останется в истории).
- Извлечение фактов light-моделью может пропускать или переформулировать факты.
- Нет многопользовательского разделения (user/session scopes, как в Mem0).

## 6. Что можно улучшить

1. Перейти на Graphiti + Kuzu (embedded) для L3, когда тяжёлый уровень станет быстрее, или оставить SQLite, добавив таблицу рёбер (entity–relation–entity) для зависимостей сервисов.
2. Консолидация («сон»): периодически сжимать похожие эпизоды в обобщённые уроки и предлагать их как новые skills (procedural learning, как в LangMem).
3. Синхронизация `INFRA.md` ↔ L3: факты с высокой уверенностью предлагать как PR в INFRA.md.
4. Калибровка порогов Jev-like (`noul ≥ 0.5`) на размеченном наборе пар фактов; Platt scaling.
5. PageIndex для длинных регламентов (если появятся многостраничные runbooks).
