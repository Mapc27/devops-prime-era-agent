# 00. Разбор задания: требования, критерии приёмки, тест-кейсы

> Статус: черновик v0.2 (2026-10-12). **Домен: DevOps/SRE-ассистент** (разбор инцидентов). Детализация use-cases — в ТЗ (`01-spec.md`); места, зависящие от домена, помечены `[DOMAIN]`.

## 1. Суть задачи в трёх предложениях

Построить **одну** автономную мультиагентную систему на локальных LLM, где агенты связаны общим флоу (оркестрация/роутинг), есть **слой верификации** (агент-валидатор на модели *другого семейства*), память из 2–3 слоёв, свои tools/skills/.md-файлы личности, всё запущено в изолированной среде и покрыто evals + observability.
Параллельно — **исследовательская часть**: сравнить движки инференса, ≥3 LLM по агентным характеристикам, фреймворки, варианты памяти и изоляции, и *обосновать* каждый выбор.
Результат — работающий репозиторий + отчёт с 7 C4-диаграммами и sequence-диаграммами, который нужно защитить устно.

Оценивается не сила моделей, а **качество обоснований** и **полнота инженерного контура** (изоляция, evals, observability).

### 3.2 Функциональные требования (F)

| ID | Требование |
|---|---|
| F-1 | **Мультиагентность**: ≥3 ролей агентов (напр. Supervisor/Router → Worker(ы) → Validator), объединённых в один граф/флоу. Не набор независимых сингл-агентов |
| F-2 | **Роутинг LLM по стоимости/сложности**: минимум 2 «уровня» моделей (малая быстрая / квантованная большая), опционально облачный API как fallback. Решение роутера логируется |
| F-3 | **Слой верификации**: агент-валидатор проверяет решения рабочих агентов; использует **LLM другого семейства**, чем исполнитель (напр. исполнитель Qwen → валидатор Gemma/Llama/Mistral/gpt-oss). Может отклонить и вернуть на доработку |
| F-4 | **Системные промпты** для каждой роли — в файлах, версионируются |
| F-5 | **Skills** — собственные файлы скиллов (формат SKILL.md: описание + инструкции + опционально скрипты), подгружаемые агентом по необходимости |
| F-6 | **Семантические .md-файлы личности/правил** (аналог SOUL.md, AGENTS.md, USER.md, TOOLS.md у OpenClaw): ценности, стиль, границы, правила эскалации |
| F-7 | **Tools**: ≥3 реальных инструмента (напр. файловая система в сандбоксе, shell/код в сандбоксе, веб-поиск/HTTP, домен-специфичные). Желательно через MCP |
| F-8 | **Память ≥ 3 слоя**: short-term (контекст/состояние графа), working/episodic (сессии, summary), long-term (факты/знания — граф/векторы). Механизм актуализации: TTL, temporal validity (bi-temporal edges), дедупликация, конфликт-резолюшн, decay |
| F-9 | **Jev-like model** (tev1/nimble через `/v1/systemone`) — control plane: классификация запроса для роутинга, выбор skill, `noul`-предпроверки в валидаторе, каскад по `confidence` |
| F-10 | Пользовательский интерфейс: CLI и/или простой web/API `[DOMAIN]` |
| F-11 | Use-cases домена DevOps/SRE: триаж алерта/инцидента → сбор логов и метрик → гипотезы о первопричине → диагностические команды в сандбоксе → план исправления → проверка валидатором на безопасность → HITL перед применением → постмортем в память. Детали в ТЗ |

## 5. Тест-кейсы (верхнеуровневые)

Детализируются после выбора домена. Типы: **U** — unit, **I** — интеграционный, **E** — eval (LLM-оценка), **S** — security, **O** — observability.

| TC | Тип | Проверяет | Сценарий | Ожидаемо |
|---|---|---|---|---|
| TC-01 | E | R-3 | Фактические вопросы с известным ответом + вопросы о несуществующих сущностях | Доля правильных; доля «не знаю» на несуществующих (галлюцинации) |
| TC-02 | E | R-3 | Задача требует вызвать tool с корректными аргументами по JSON-схеме | Валидный tool call ≥ X% |
| TC-03 | E | R-3 | Многошаговая задача (2–4 tool calls) | Успешное завершение, число шагов |
| TC-04 | E | R-3 | Строгий JSON-формат вывода | Парсинг без ошибок |
| TC-05 | E | R-3 | Needle-in-haystack на 8–32k контекста | Найдено/не найдено |
| TC-06 | E | R-3 | Инструкция-ловушка (prompt injection в tool output) | Модель не выполняет внедрённую инструкцию |
| TC-07 | I | F-1 | Запрос пользователя проходит Router→Worker→Validator→ответ | Трейс содержит все узлы |
| TC-08 | I | F-2 | «Привет» vs сложный многошаговый запрос | Разные модели в трейсе |
| TC-09 | I | F-3 | Worker подменён моком, возвращающим неверный ответ | Validator reject → retry → max_retries → эскалация |
| TC-10 | U | F-3 | Конфиг валидатора | `family(validator) != family(worker)`, иначе ошибка старта |
| TC-11 | I | F-5 | Запрос, требующий конкретный skill | Skill загружен (видно в трейсе), не загружены лишние |
| TC-12 | I | F-6 | Изменение правила в SOUL.md (напр. «никогда не делай X») | Поведение меняется |

## 6. Метрики evals (заготовка, 4 категории)

- **Продуктовые**: task success rate, % эскалаций к человеку, удовлетворённость (thumbs up/down), time-to-resolution, % запросов, решённых без ретраев.
- **Агентные**: tool-call accuracy, trajectory efficiency (шагов на задачу vs эталон), validator reject rate, retry rate, loop/stuck rate, memory recall precision, доля роутинга на малую модель.
- **LLM-уровня**: correctness / faithfulness / groundedness, hallucination rate, JSON-validity, instruction following, LLM-as-judge (judge другого семейства), токены in/out.
- **Инфраструктурные**: TTFT, tok/s, p50/p95/p99 latency, RAM/VRAM, CPU, ошибки движка, cold start сандбокса, «стоимость» (токены × условная цена / энергия).

## 8. Открытые вопросы

1. **Домен агента** — что именно делает система? (определяет tools, skills, eval-набор, use-cases).
2. ~~«Jev-like Model»~~ — решено: это класс моделей, похожих на **Jev** от TypeSafe AI (15.09.2026, https://habr.com/ru/articles/1085450/). Это System One модели принятия решений: они не генерируют текст, а через `/v1/systemone` возвращают вероятности по примитивам `choice`, `noul` и `score` вместе с `confidence`. Локальные аналоги: `tev1` (Together AI) и `nimble` (Bespoke Labs) в Ollama ≥ 0.35. В системе работает как control plane: роутинг, выбор skill, дешёвые проверки валидатора, каскады. Подробности в `02-models-shortlist.md`.
3. ~~Облачный API~~ — решено: Claude как верхний (облачный) уровень роутинга и fallback. **Важно:** подписка Claude Pro **не даёт доступа к API** — API оплачивается отдельно по факту использования (console.anthropic.com, нужен API-ключ). Использовать подписку через неофициальные обходы нельзя (нарушает условия). Варианты: (а) завести API-ключ и пополнить баланс на ~$5–10 — для этого объёма хватит с запасом; (б) если без оплаты — облачный уровень через бесплатные лимиты другого провайдера или только локальный роутинг. Слой абстракции (LiteLLM) делает провайдера заменяемым — решение не блокирует работу.
