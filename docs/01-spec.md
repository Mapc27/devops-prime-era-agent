# 01. Техническое задание: мультиагентный SRE-ассистент «Ops Crew»

> Статус: v0.1 (2026-10-12). Рабочее название — **Ops Crew**. Требования ссылаются на ID из `00-task-analysis.md`.

## 1. Назначение

Ops Crew — автономная мультиагентная система, которая **расследует инциденты** в инфраструктуре: принимает алерт или вопрос дежурного, сама собирает логи и метрики, выдвигает и проверяет гипотезы о первопричине, предлагает исправление, проверяет его безопасность отдельным агентом-валидатором, **после подтверждения человеком** применяет исправление в изолированной среде и пишет постмортем, который попадает в долговременную память.

**Почему этот домен хорошо ложится на задание:**
- агент выполняет команды — значит, изоляция нужна по существу, а не для галочки (N-1);
- ошибка агента дорогая (`rm -rf`, рестарт прод-БД) — значит, слой валидации и HITL обязательны (F-3, N-6);
- инциденты повторяются — значит, долговременная память с актуализацией даёт измеримую пользу (F-8);
- у инцидента есть известная первопричина — значит, evals можно сделать объективными (N-3).

## 2. Пользователи и сценарии

| Актор | Что делает |
|---|---|
| Дежурный инженер (SRE/DevOps) | Задаёт вопросы, получает диагноз, подтверждает или отклоняет действия |
| Alertmanager (система) | Присылает алерт через webhook, тем самым запуская расследование |
| Преподаватель / ревьюер | Смотрит трейсы, дашборды и отчёт evals |

### 2.1 Use-cases

| UC | Название | Триггер | Результат |
|---|---|---|---|
| UC-1 | Простой вопрос | «Что такое OOMKilled?», «Покажи статус сервисов» | Быстрый ответ малой моделью без тяжёлого флоу |
| UC-2 | **Расследование инцидента** (основной) | Алерт `HighErrorRate api` или текст дежурного | Диагноз с доказательствами: цитаты логов, значения метрик, уверенность |
| UC-3 | Исправление с HITL | Продолжение UC-2 | План действий → валидатор → подтверждение человека → выполнение в сандбоксе → проверка, что метрики восстановились |
| UC-4 | Повторный инцидент | Похожий алерт через N дней | Агент вспоминает прошлый постмортем и решает быстрее (меньше шагов) |
| UC-5 | Обновление знаний | «Мы переехали с Postgres 15 на 17», «Redis больше не используем» | Старый факт инвалидируется, новый становится актуальным |
| UC-6 | Опасный запрос | «Удали все логи, чтобы освободить место», prompt injection в логах | Отказ или эскалация; инъекция не исполняется |

### 2.2 Учебный стенд («лаборатория инцидентов»)

Реального прода нет, поэтому строим **стенд с внедряемыми сбоями** — он же основа evals:
- docker-compose: `api` (FastAPI), `worker`, `postgres`, `redis`, `nginx`, а также Prometheus, Loki и Grafana;
- скрипт `chaos/` внедряет сбой с известной первопричиной: заполнение диска, утечка памяти → OOM, исчерпание пула соединений к БД, неверный конфиг после «деплоя», падение redis, медленный запрос, истёкший сертификат, DNS;
- каждый сценарий описан в YAML: `trigger`, `ground_truth_root_cause`, `expected_evidence`, `safe_fix`, `forbidden_actions`.

## 3. Архитектура агентов (верхний уровень)

Детальные C4- и sequence-диаграммы будут в `04-architecture.md`. Здесь фиксируем роли.

| # | Агент | Ответственность | Модель (гипотеза до бенчмарка) |
|---|---|---|---|
| A0 | **Triage Router** (Jev-like) | Классифицирует вход: `choice` — тип (вопрос / инцидент / изменение знаний / опасное), `score` — серьёзность, `choice` — сложность → выбор пути и уровня модели | `tev1:4b` через `/v1/systemone` |
| A1 | **Supervisor** | Строит план расследования, делегирует подзадачи, собирает итог, решает, когда остановиться | тяжёлый уровень (`qwen3.8:27b` / `muse-glimmer:30b`) |
| A2 | **Investigator** | Ходит в логи, метрики и статус контейнеров, проверяет гипотезы, собирает доказательства | лёгкий уровень (`granite4.2:8b` / `ornith:9b`), эскалация на тяжёлый |
| A3 | **Knowledge agent** | Достаёт из памяти похожие инциденты, runbooks и факты об инфраструктуре | лёгкий уровень + эмбеддинги |
| A4 | **Remediator** | Формирует план исправления (команды и диффы), делает dry-run в сандбоксе | тяжёлый уровень |
| A5 | **Validator** | Проверяет диагноз (каждое утверждение подкреплено доказательством из трейса) и план (безопасность, обратимость, соответствие политике). Вердикт `approve` / `revise` (с замечаниями) / `escalate` | **другое семейство**: `gemma4:12b` (Google) + Jev-like `noul`-предпроверки |
| A6 | **Scribe** | Пишет постмортем, извлекает факты и обновляет долговременную память | лёгкий уровень |
| H | **Human gate** | Подтверждает любое изменяющее действие | человек (CLI / UI) |

**Флоу UC-2/3 (кратко):**
`Alert → A0 Triage → A1 Supervisor ⇄ (A2, A3) → диагноз → A5 Validator → [revise → A1] → A4 Remediator → A5 Validator → H Human gate → выполнение в сандбоксе → A2 проверка восстановления → A6 Scribe → память`

**Ограничители:** не больше N итераций revise (по умолчанию 2), бюджет шагов и токенов на расследование, тайм-аут; при исчерпании — эскалация человеку с промежуточными находками.

## 4. Функциональные требования (детализация)

### 4.1 Роутинг моделей (F-2)
- Уровни: `L0` Jev-like (решения), `L1` малая/средняя локальная модель, `L2` большая квантованная локальная модель, `L3` облако (опционально, fallback).
- Правила: Triage `complexity=simple` → L1. `complex` или `confidence < τ` → L2. Падение или тайм-аут L2 → L3 (если включено) или L1 с пометкой «degraded».
- Все вызовы идут через единый шлюз (LiteLLM proxy): OpenAI-совместимый API, учёт токенов, fallback, условная стоимость.
- Решение роутера (уровень, причина, confidence) пишется в атрибуты трейса.

### 4.2 Валидатор (F-3)
- Проверка семейства при старте: если `family(validator) ∈ families(workers)`, система не запускается.
- Чек-лист валидатора:
  1. **Grounding:** каждое утверждение диагноза ссылается на `evidence_id` из реальных tool-результатов (проверяется программно и моделью).
  2. **Safety:** деструктивные операции (удаление данных, `DROP`, `rm -rf`, `docker volume rm`, рестарт stateful-сервисов) → `escalate`.
  3. **Reversibility:** у плана есть шаг отката.
  4. **Policy:** соответствие правилам из `GUARDRAILS.md`.
- Дешёвые проверки первыми (regex/AST-allowlist → Jev-like `noul`), затем LLM-валидатор. Так экономим токены и время.

### 4.3 Системные промпты (F-4)
- `prompts/<agent>.md` для каждой роли: роль, цели, входы и выходы (JSON-схема), запреты, формат доказательств.
- Версия промпта пишется в трейс (`prompt.version`) — для сравнения в evals.

### 4.4 Файлы личности и правил (F-6), по мотивам OpenClaw
| Файл | Содержание |
|---|---|
| `SOUL.md` | Ценности и характер: осторожность важнее скорости, «не уверен — скажи», не выдумывать метрики, уважение к дежурному в 3 часа ночи |
| `AGENTS.md` | Роли агентов, протокол передачи задач, кто за что отвечает |
| `GUARDRAILS.md` | Запрещённые и требующие подтверждения действия, правила эскалации |
| `INFRA.md` | Описание стенда: сервисы, зависимости, SLO (подгружается в контекст и синхронизируется с памятью) |
| `USER.md` | Предпочтения дежурного (язык, детальность, каналы) — обновляется из памяти |
| `TOOLS.md` | Когда какой инструмент использовать, типичные ошибки |

### 4.5 Skills (F-5)
Формат `skills/<name>/SKILL.md`: frontmatter `name`, `description`, `when_to_use`, затем пошаговая инструкция и опционально `scripts/`. Агент видит только описания всех skills и подгружает полный текст по требованию (progressive disclosure). Выбор skill делает Jev-like `choice` или сама модель.

Минимальный набор:
1. `triage-http-5xx` — расследование роста ошибок 5xx
2. `diagnose-oom` — OOMKilled и утечки памяти
3. `disk-pressure` — заполнение диска (с безопасной очисткой)
4. `db-connection-exhaustion` — исчерпание пула соединений
5. `bad-deploy-rollback` — откат неудачного конфига или деплоя
6. `write-postmortem` — шаблон постмортема (blameless)

### 4.6 Tools (F-7)
Выставляются через **MCP-сервер** `ops-tools` (стандартный протокол, переиспользуемость):

| Tool | Тип | Где выполняется | Ограничения |
|---|---|---|---|
| `query_metrics(promql, range)` | read | Prometheus API | только чтение |
| `query_logs(logql, range, limit)` | read | Loki API | лимит строк, обрезка; вывод помечается как **untrusted** |
| `list_services()` / `inspect_service(name)` | read | docker API стенда (через прокси с allowlist) | read-only |
| `run_diagnostic(cmd)` | exec | **в сандбоксе** | allowlist команд (`df`, `free`, `ss`, `curl` к стенду, `psql -c SELECT…`) |
| `apply_fix(plan_id)` | write | в сандбоксе на стенде | только после `approve` валидатора **и** подтверждения человека |
| `search_memory(query)` / `remember(fact)` | memory | memory service | — |
| `load_skill(name)` | meta | локально | — |
| `create_ticket(summary)` | write (mock) | заглушка | — |

### 4.7 Память (F-8) — предварительно, обоснование в `05-memory.md`
| Слой | Что хранится | Время жизни | Реализация (кандидат) |
|---|---|---|---|
| L1 Short-term / working | Состояние графа текущего расследования: сообщения, гипотезы, доказательства | Одно расследование | State графа + checkpointer (SQLite/Postgres) |
| L2 Episodic | Резюме прошлых расследований и постмортемы | Месяцы, с затуханием релевантности | Postgres + pgvector (гибридный поиск) |
| L3 Semantic / long-term | Факты об инфраструктуре и пользователе с временной валидностью («api зависит от redis» valid_from/valid_to) | До инвалидации | Темпоральный граф знаний (Graphiti / Mem0 graph) |
| (L0) Procedural | Skills и runbooks | Версионируются в git | Файлы `skills/` |

Актуальность: bi-temporal рёбра (новый факт закрывает старый), TTL для эпизодов, дедупликация при записи, периодическая «консолидация», источник и время у каждого факта.

## 5. Нефункциональные требования (детализация)

| ID | Требование | Целевое значение |
|---|---|---|
| N-1 | Изоляция | Агентный рантайм и выполнение команд — в Docker Sandbox (microVM) или контейнере с `--read-only`, `cap-drop=ALL`, без docker.sock, с сетевым allowlist. LLM-движок — на хосте |
| N-2 | Observability | 100% запросов трассируются (OTel → Langfuse); метрики → Prometheus/Grafana; логи → Loki; ≥3 алерта |
| N-3 | Evals | ≥30 сценариев; прогон одной командой; регресс между версиями промптов и моделей |
| N-5 | Латентность | UC-1 ≤ 5 с (p95); UC-2 диагноз ≤ 3 мин (p95) на локальных моделях |
| N-5 | Память | Пиковое потребление моделей ≤ 18 GB |
| N-6 | Безопасность | 0 выполненных деструктивных действий без HITL на всём eval-наборе; 0 успешных инъекций из логов |
| N-7 | Offline | Полный функционал без интернета (облачный уровень выключен) |

## 8. Критерии приёмки ТЗ

См. `00-task-analysis.md` §4. Дополнительно для домена:
- AC-UC2: на ≥70% сценариев стенда первопричина определена верно (на тяжёлом уровне).
- AC-UC3: после применения fix метрики сценария возвращаются в норму, это проверяется автоматически.
- AC-UC4: на повторном сценарии число шагов меньше, чем при первом прохождении (эффект памяти).
- AC-UC6: все сценарии опасных запросов и инъекций завершаются отказом или эскалацией.
